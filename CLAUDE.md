# CLAUDE.md

Standing instructions for Claude Code in this repo. Read this and `SPEC.md` at the start of every session.

## What this project is

A WTA match and tournament simulator. Tennis scoring and tournament rules are written in Bend 2, with their correctness proven by laws in `engine/LAWS.bend`. A small TypeScript layer handles data prep, an exact calculator for checking, and anything touching files or text. The first goal is publishing 2026 WTA Finals odds before November 8.

`SPEC.md` is the source of truth. If something here conflicts with it, `SPEC.md` wins. Flag the conflict instead of choosing silently.

## How we work

- **One milestone at a time.** Do only the milestone you were asked for, then stop and summarise. Never start the next milestone unprompted.
- **End every milestone with a summary** covering:
  - what was built;
  - which laws were added and whether they prove;
  - what failed or surprised you;
  - open questions.
- **Explain Bend as you go.** The owner is learning Bend through this project. When a milestone introduces a new Bend concept (a law, a proof, a type, a parallel split), explain it in a few plain sentences in the summary.
- **Propose spec changes; don't make them.** If the spec looks wrong or incomplete, describe the problem and a suggested fix in your summary. Edit `SPEC.md` only after the owner agrees.
- **Ask rather than guess** about tennis rules, data or anything the spec leaves open.
- **Keep a progress log.** Add a short, plain-language entry to `docs/progress.md` for each milestone: what works now, one interesting finding, and a number or screenshot-worthy output if there is one. The owner posts progress publicly, so write it for a general reader.

## Bend rules (most important section)

- **Never weaken, delete or work around a law to make code compile.** If a law won't prove, stop and report: the law may be wrong, or the code may be. The owner decides which.
- **Write laws before implementation.** For each layer (game, tiebreak, set, match, standings, knockouts), add its laws from the spec's Laws section first, then write code that satisfies them.
- **Bend 2 is not Bend 1.** Most older examples online, and much of what you may remember, are for the earlier Bend on HVM2, which had different syntax and features. Check Bend 2's own guide and docs before writing code. If unsure, write a tiny test file and compile it.
- **No decimals in the engine.** Probabilities are whole numbers out of 10,000 (60% = 6000).
- **Every recursion must end.** Each match draws from at most 1,000 points. A match that hits the cap is reported as unfinished, never silently counted.
- **Random numbers are counter-based**, derived from the run seed and the simulation index. Simulations never share state.
- **Never hand-edit `engine/params.bend`.** It is generated by `prep/`.
- **Record toolchain facts** in `docs/bend-notes.md`: the Bend version, install steps, commands that work, and quirks or bugs found. Bend 2 is young and expected to have bugs; note them rather than fighting them silently.

## TypeScript rules

- TypeScript on Node (current LTS). Ask before adding another runtime or any dependency beyond a CSV parser and a test runner.
- `prep/` turns `data/players.csv` into `engine/params.bend`, using the point model chosen in the spec (average method first, additive from milestone 5).
- The exact calculator lives in `prep/` and must never share code with the Bend engine. Its value is being an independent check.

## Validation (before calling a milestone done)

- All laws in `engine/LAWS.bend` prove.
- From milestone 4 on: the simulator matches the exact calculator within 0.2 percentage points across the input grid in the spec.
- Sanity cases pass: equal players give 50/50; swapping players swaps the result; the same seed gives identical output.

## Data rules

- **Never invent player stats.** If a value is missing from `data/players.csv`, leave it blank and ask.
- Tournament format and standings tiebreak rules come only from the official text saved in `data/rules/`. If that folder is empty when a milestone needs it, stop and ask.
- Data derived from Tennis Abstract / Jeff Sackmann is licensed CC BY-NC-SA 4.0. Keep the project non-commercial, and credit the source on the results page and in the README.

## Out of scope for v0

Don't build these, even if they seem easy: opponent-strength adjustment, shrinkage, recency weighting, big-point modelling, fatigue, withdrawals, GPU targets, or events other than the WTA Finals. Mention ideas in summaries instead.

## Git

- One branch per milestone (`m1-setup`, `m2-game-layer`, and so on), small commits with clear messages.
- Each pull request description repeats the milestone summary.
- Commit results CSVs only for published runs, named with date and seed.
